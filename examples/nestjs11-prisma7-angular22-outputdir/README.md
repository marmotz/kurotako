# nestjs11-prisma7-angular22-outputdir

End-to-end example: NestJS 11 + Angular 22 + Prisma 7 (DMMF mode), consuming kurotako's
**mode A** (`dir`) output — one `generated/kurotako` destination per app.

- `apps/backend` gets a Zod-only destination (only ever imports validators).
- `apps/frontend` gets an unrestricted destination (Zod schemas + Angular form factories).

This project is a fully standalone Bun workspace, independent of the kurotako repo's
own root workspace (`workspaces: ["apps/*"]` here only).

## Setup

Kurotako packages are not published yet (all pinned at `0.0.0`), so this project
consumes them via `bun link` from a local clone of the kurotako repo:

```bash
# from the kurotako repo root, once, after any change to a linked package:
bun run build
cd packages/cli            && bun link && cd -
cd packages/config          && bun link && cd -
cd packages/parser-prisma   && bun link && cd -
cd packages/gen-zod         && bun link && cd -
cd packages/gen-angular     && bun link && cd -
```

```bash
# from this project's root, once per clone:
bun link @kurotako/cli @kurotako/config @kurotako/parser-prisma @kurotako/gen-zod @kurotako/gen-angular
bun install
```

`package.json` pins the five kurotako packages with the `link:@kurotako/<name>`
specifier rather than a plain `0.0.0` semver range: since these packages are not
published, a semver-range specifier makes `bun install` try (and fail, 404) to resolve
them from the npm registry even after `bun link` has registered the local symlink —
`link:` is the specifier `bun link` itself prints and is required for `bun install` to
leave the linked symlink alone. Once kurotako publishes, swap these back to a real
version range and drop the `bun link` steps above.

`@prisma/internals` is a direct devDependency here (not just `prisma`): `parser-prisma`
needs it at runtime to read `schema.prisma` in DMMF (`version: 7`) mode — this refers to
`parser-prisma`'s DMMF-vs-`contract.json` parsing mode, not the Prisma npm major version,
though this project happens to pin the actual `prisma`/`@prisma/client` packages at their
current major (7.x) too.

Prisma 7 moved connection config out of `schema.prisma` into `prisma.config.ts` (root of
this project) and requires an explicit driver adapter at the `PrismaClient` call site —
`apps/backend/src/prisma/prisma.service.ts` constructs one from
`@prisma/adapter-better-sqlite3`. The generator also changed from `prisma-client-js` to
`prisma-client` with a required `output` path (`schema.prisma`'s `generator client`
block) — the client is generated as plain `.ts` sources into `apps/backend/generated/prisma`
(gitignored, regenerated by `prisma generate`), imported with explicit `.js` specifiers
per this project's `"module": "nodenext"` tsconfig (resolved back to the `.ts` source by
TypeScript — Jest needs a `moduleNameMapper` for the same rewrite, already set up in
`apps/backend/test/jest-e2e.json`). Its WASM query compiler is loaded through a dynamic
`import()`, which Jest's default CJS runtime refuses without
`NODE_OPTIONS=--experimental-vm-modules` (already set on the `test:e2e` script) — `nest
start`/`node dist/main` need no such flag.

## Generate

```bash
bun run prisma:generate   # prisma generate — Prisma Client for apps/backend
bun run prisma:migrate    # prisma migrate dev — creates apps/backend/prisma/dev.db
bun run tako:generate     # tako generate — writes apps/{backend,frontend}/generated/kurotako
```

`tako generate` must run again after any `schema.prisma` change — the generated output
is gitignored (regenerable, not committed).

Each app's `tsconfig.json` declares a `"tasks/*"` path alias pointing at its own
`generated/kurotako/tasks/*` — the generated files import each other through that
bare `tasks/...` specifier (the namespace declared in `tako.config.ts`'s `sources`),
not a relative path.

## Run

```bash
cd apps/backend && bun run start:dev    # NestJS on http://localhost:3000
cd apps/frontend && bun run start       # Angular dev server
```

Try it:

```bash
curl http://localhost:3000/tasks
curl -X POST http://localhost:3000/tasks -H 'content-type: application/json' \
  -d '{"title":"write docs"}'   # missing projectId -> 400 with Zod issues
```
