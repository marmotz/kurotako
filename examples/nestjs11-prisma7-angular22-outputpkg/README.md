# nestjs11-prisma7-angular22-outputpkg

End-to-end example: NestJS 11 + Angular 22 + Prisma 7 (DMMF mode), consuming kurotako's
**mode B** (`package`) output — one shared `@example/tasks` workspace package consumed
by both apps.

Both generators run against `relations: 'deep'`: the generated `Task` form nests a
`FormGroup`/field for `project` (required) and one for `assignee` (optional), instead of
the flat `projectId`/`assigneeId` scalars the `outputdir` example exercises.

This project is a fully standalone Bun workspace, independent of the kurotako repo's
own root workspace (`workspaces: ["apps/*", "packages/*"]` here only — `packages/*` is
required so `@example/tasks` resolves as a workspace member once `tako generate` writes
it).

## Setup

Kurotako packages are not published yet (all pinned at `0.0.0` upstream), so this
project consumes them via `bun link` from a local clone of the kurotako repo:

```bash
# from the kurotako repo root, once, after any change to a linked package:
bun run build
cd packages/cli            && bun link && cd -
cd packages/config          && bun link && cd -
cd packages/parser-prisma   && bun link && cd -
cd packages/gen-zod         && bun link && cd -
cd packages/gen-angular     && bun link && cd -
```

```bash
# from this project's root, once per clone:
bun link @kurotako/cli @kurotako/config @kurotako/parser-prisma @kurotako/gen-zod @kurotako/gen-angular
bun install
```

`package.json` pins the five kurotako packages with the `link:@kurotako/<name>`
specifier — see the `outputdir` example's README for why a plain `0.0.0` semver range
does not survive `bun install` once linked.

Mode B additionally needs `tsup` (build) and `typescript` at the workspace root — the
`packageWriter` builds `packages/example-tasks` with them — plus `@angular/core`,
`@angular/forms` and `zod` as devDependencies so its own `dts` build can resolve the
peer types the generated Angular/Zod code imports. Also, mode B requires
`tsconfig.base.json` **and** `tsup.config.base.ts` at the workspace root (one directory
above `packagesDir`) — `tako generate` fails fast with the exact files/content it
expects if either is missing.

Prisma 7 moved connection config out of `schema.prisma` into `prisma.config.ts` (root of
this project) and requires an explicit driver adapter at the `PrismaClient` call site —
`apps/backend/src/prisma/prisma.service.ts` constructs one from
`@prisma/adapter-better-sqlite3`. The generator also changed from `prisma-client-js` to
`prisma-client` with a required `output` path (`schema.prisma`'s `generator client`
block) — the client is generated as plain `.ts` sources into `apps/backend/generated/prisma`
(gitignored, regenerated by `prisma generate`), imported with explicit `.js` specifiers
per this project's `"module": "nodenext"` tsconfig (resolved back to the `.ts` source by
TypeScript — Jest needs a `moduleNameMapper` for the same rewrite, already set up in
`apps/backend/test/jest-e2e.json`). Its WASM query compiler is loaded through a dynamic
`import()`, which Jest's default CJS runtime refuses without
`NODE_OPTIONS=--experimental-vm-modules` (already set on the `test:e2e` script) — `nest
start`/`node dist/main` need no such flag.

## Generate

```bash
bun run prisma:generate   # prisma generate — Prisma Client for apps/backend
bun run prisma:migrate    # prisma migrate dev — creates apps/backend/prisma/dev.db
bun run tako:generate     # tako generate — writes packages/example-tasks, builds it, and
                           # runs `bun install` to link it into apps/backend + apps/frontend
```

`tako generate` must run again after any `schema.prisma` change. `packages/example-tasks`
is entirely regenerable (gitignored) — every file under it, including `package.json`, is
written by `tako generate`.

Import subpaths from `@example/tasks` must target the concrete file, not a directory
barrel that only exists as `index.ts` — e.g. `@example/tasks/zod/index`, not
`@example/tasks/zod` (the package's `"./*"` export map is a flat wildcard, so it does not
resolve a bare `zod` to `zod/index`).

**Known limitation:** `@example/tasks/angular/*` (`Task.form.ts`, `Project.form.ts`,
`User.form.ts`) declares `@Injectable` reactive factory classes (`TaskFormFactory` and
friends) alongside the Signal Forms free functions, in the same file. Mode B's
`packageWriter` builds with tsup/esbuild, not `ng-packagr` — esbuild never emits the
`design:paramtypes` metadata Angular's DI needs for a decorated class, so merely
importing anything from those files crashes the app at load time (`NG0202`), even code
that never touches the class. `apps/frontend`'s components route around this: the
reactive create form is hand-built with plain `FormGroup`/`FormControl`, and the signal
forms edit form is hand-built with `form()`/`schema()` from `@angular/forms/signals`
directly — both still validate through the real generated `TaskCreateDeepSchema` /
`TaskUpdateDeepSchema` and the generated `zodTreeValidate` runtime helper
(`@example/tasks/angular/zod-forms.runtime`, which has no such class and loads fine).
The `outputdir` example is unaffected: mode A writes plain `.ts` sources straight into
each app, compiled by the app's own Angular AOT pipeline, not tsup.

## Run

```bash
cd apps/backend && bun run start:dev    # NestJS on http://localhost:3000
cd apps/frontend && bun run start       # Angular dev server
```

Try it:

```bash
curl http://localhost:3000/tasks
curl -X POST http://localhost:3000/tasks -H 'content-type: application/json' \
  -d '{"title":"write docs"}'   # missing projectId -> 400 with Zod issues
```
