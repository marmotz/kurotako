# OpenAPI generator — technical design

See [overview.md](overview.md) for the product-level decisions this design
implements (schemas-only scope, JSON+YAML output, symmetric union mapping).

## Package layout

Mirrors `@kurotako/gen-zod` / `@kurotako/gen-angular`'s structure
([`packages/gen-zod/src`](../../../packages/gen-zod/src),
[`packages/gen-angular/src`](../../../packages/gen-angular/src)):

```
packages/gen-openapi/
  src/
    index.ts            # public entry point: driver + options type + error classes
    generator.ts         # defineGenerator({ name: 'openapi', ... })
    options.ts            # OpenApiGeneratorOptions (Valibot)
    document.ts            # assembles the OpenAPI document object for one namespace
    serialize.ts           # document -> JSON / YAML string
    render/
      schema.ts             # FieldType -> JSON Schema fragment
      entity.ts               # Entity -> components/schemas/<Entity> object
      constraints.ts            # Constraints -> JSON Schema keywords
    errors.ts
    testing/
      ir.ts                    # SourceIR/Entity test builders (mirrors gen-zod's testing/ir.ts)
  package.json
  tsup.config.ts
```

No `dialect.ts`-equivalent: unlike Zod's v3/v4 API split, the OpenAPI 3.0 vs
3.1 difference is confined to how nullability and `type` are expressed (see
"Nullability" below) — a single conditional in `render/schema.ts`, not a
family of leaf builders.

## Options

```ts
// options.ts
import * as v from 'valibot';

export const OpenApiGeneratorOptions = v.object({
  openapiVersion: v.optional(v.picklist(['3.0', '3.1']), '3.1'),
  format: v.optional(v.picklist(['json', 'yaml']), 'json'),
  title: v.optional(v.string()),   // default: the namespace, applied in generate()
  version: v.optional(v.string(), '0.0.0'),
});

export type OpenApiGeneratorOptions = v.InferOutput<typeof OpenApiGeneratorOptions>;
```

`title` has no static Valibot default (it depends on the namespace, which
`options.ts` cannot see), so `generator.ts` applies `options.title ?? namespace`
per source when assembling `info`.

## Generator driver

```ts
// generator.ts
export const openapiGenerator = defineGenerator({
  name: 'openapi',
  optionsSchema: OpenApiGeneratorOptions,

  generate(ctx: GenerateContext, options): GenOutput {
    const files: VirtualFile[] = [];
    for (const [namespace, source] of Object.entries(ctx.ir.sources)) {
      const document = buildDocument(ctx.ir, source, options, namespace);
      const ext = options.format === 'yaml' ? 'yaml' : 'json';
      files.push({
        path: `${namespace}/openapi/openapi.${ext}`,
        content: serialize(document, options.format),
      });
    }
    return { files, artifact: buildArtifact(ctx.ir) };
  },
});
```

One `VirtualFile` per namespace (decided: a single `openapi.<ext>` document,
not one file per entity — a spec is normally not split, and external tooling
consuming it expects one document). No barrel: nothing else lives under
`<namespace>/openapi/`.

`applyBanner` ([`packages/core/src/writer/banner.ts`](../../../packages/core/src/writer/banner.ts))
only prepends the `// Generated by tako` comment to `.ts`/`.tsx` files (plus
`tsconfig.json`); `openapi.json` / `openapi.yaml` get no banner and no
`"//"` marker, same as the rest of `.json` output today. Out of scope for
this feature to change that (tracked implicitly by whatever future work
touches `banner.ts` for non-TS generators in general — `gen-openapi` is not
special-cased).

## Document assembly (`document.ts`)

```ts
interface OpenApiDocument {
  openapi: string;                     // "3.0.3" | "3.1.0" (pinned patch, see below)
  info: { title: string; version: string };
  paths: Record<string, never>;        // always {} — scope excludes paths/operations
  components: { schemas: Record<string, unknown> };
}
```

- `openapi`: `"3.0.3"` or `"3.1.0"` depending on `options.openapiVersion` —
  pinned patch versions rather than bare `"3.0"` / `"3.1"`, since `openapi`
  must be a full semver-like string per the spec (`parser-openapi`'s
  `/^3\.[01]/` check in
  [`packages/parser-openapi/src/parser.ts:330-334`](../../../packages/parser-openapi/src/parser.ts#L330-L334)
  accepts either).
- `paths: {}`: always present and empty. An empty object is valid per the
  OpenAPI spec and keeps the document immediately usable by tools that
  assume the key exists.
- `components.schemas`: one entry per `Entity` in `source.entities`, plus one
  entry per `SourceIR.typeAliases` (unions, refs-only aliases, enums —
  `parser-openapi` produces these for `oneOf`/`anyOf` roots and inline
  enums, see
  [`packages/parser-openapi/src/parser.ts:443-464`](../../../packages/parser-openapi/src/parser.ts#L443-L464));
  emitting both keeps a spec → IR → spec round-trip stable for a document
  that started life through `parser-openapi`.
- Entity/alias name collisions: none possible — both live in the same flat
  `components/schemas` namespace, and the IR's cross-reference pass already
  guarantees `entities` and `typeAliases` keys don't collide within one
  `SourceIR` (`docs/ir.md` "Closed points" §3).

## Field-type mapping (`render/schema.ts`)

Symmetric to `parser-openapi`'s `mapSchema`
([`packages/parser-openapi/src/parser.ts:206-317`](../../../packages/parser-openapi/src/parser.ts#L206-L317)),
inverted:

| IR `FieldType.kind` | Emitted JSON Schema |
|---|---|
| `scalar: 'string'` | `{ type: 'string' }` (+ `format` from constraints, see below) |
| `scalar: 'boolean'` | `{ type: 'boolean' }` |
| `scalar: 'int'` | `{ type: 'integer' }` |
| `scalar: 'bigint'` | `{ type: 'integer', format: 'int64' }` |
| `scalar: 'float'` | `{ type: 'number' }` |
| `scalar: 'decimal'` | `{ type: 'number' }` (no lossless JSON Schema representation; same approximation `parser-openapi` makes in reverse — `number` never round-trips back to `decimal` today, an accepted asymmetry, not something this feature fixes) |
| `scalar: 'date'` | `{ type: 'string', format: 'date' }` |
| `scalar: 'datetime'` | `{ type: 'string', format: 'date-time' }` |
| `scalar: 'uuid'` | `{ type: 'string', format: 'uuid' }` |
| `scalar: 'bytes'` | `{ type: 'string', format: 'byte' }` |
| `scalar: 'json'` | `{}` (unconstrained — `parser-openapi` has no path that produces `json`, so there's no reverse mapping to mirror; an empty schema is the honest "anything" representation) |
| `enum` | `{ $ref: '#/components/schemas/<ref>' }` (enums are always named — see `typeAliases` above; `parser-openapi` never inlines enum values on read either) |
| `unknown` | `{}` (mirrors `parser-openapi`'s catch-all mapping to `unknown`, both directions) |
| `ref` | `{ $ref: '#/components/schemas/<ref>' }` |
| `map: { value }` | `{ type: 'object', additionalProperties: <mapped value>, propertyNames: undefined }` — `value.kind === 'unknown'` emits `additionalProperties: true` (symmetric with `parser-openapi:293-297`) |
| `array: { element }` | `{ type: 'array', items: <mapped element> }` |
| `union: { variants, discriminator }` | `{ oneOf: [<mapped variants>] }`; when `discriminator` is set, add `discriminator: { propertyName, mapping? }` — `mapping` re-expands each target name back to a `#/components/schemas/<name>` pointer, inverting `pointerName()` at [`packages/parser-openapi/src/parser.ts:201-204`](../../../packages/parser-openapi/src/parser.ts#L201-L204) |

`Field.list` (legacy boolean, still present alongside `FieldType.kind ===
'array'` per `docs/ir.md`) wraps the mapped type one more time in `{ type:
'array', items: ... }` when true — same double representation
`parser-openapi` itself straddles today (`entry.list = true` set alongside a
`mapSchema` call, [`packages/parser-openapi/src/parser.ts:421`](../../../packages/parser-openapi/src/parser.ts#L421)).
This is pre-existing IR ambiguity (also the subject of the currently-failing
typecheck on `develop` after the `array` `FieldType` addition, unrelated to
this feature) — `render/schema.ts` handles both without trying to resolve
which one is authoritative; if a field sets both `list: true` and
`type.kind === 'array'`, the outer `list` wrapping is skipped (no double
array-of-array) and only `type.kind`'s own `element` nesting applies.

## Constraints (`render/constraints.ts`)

Symmetric to `field()` at
[`packages/parser-openapi/src/parser.ts:161-199`](../../../packages/parser-openapi/src/parser.ts#L161-L199):

| IR `Constraints` field | Emitted keyword |
|---|---|
| `min` | `minimum` |
| `max` | `maximum` |
| `minLength` | `minLength` |
| `maxLength` | `maxLength` |
| `regex` | `pattern` |
| `format` (`StringFormat`) | `format`, using the inverse of `STRING_FORMATS` ([`packages/parser-openapi/src/parser.ts:44-52`](../../../packages/parser-openapi/src/parser.ts#L44-L52)): `email → email`, `url → uri`, `ipv4 → ipv4`, `ipv6 → ipv6`, `time → time`, `duration → duration`; `datetime`/`date`/`uuid`/`cuid`/`cuid2`/`ulid` are not string `Constraints.format` values that reach here — they only ever arise from `scalar` mapping above (`uuid`, `date`, `datetime` scalars) or have no OpenAPI equivalent (`cuid`/`cuid2`/`ulid` emit no `format`, same escape `parser-openapi` takes on an unrecognised format: silently drop rather than fail) |
| `unique` | not emitted — OpenAPI/JSON Schema has no uniqueness keyword for object properties (`uniqueItems` only applies to arrays, a different concept); dropped silently, same asymmetry `parser-prisma` already accepts for the reverse direction |

`Field.default` is not emitted as JSON Schema `default`: a DB-side
`{ kind: 'expr' }` default (`now()`, `autoincrement()`) has no JSON
representation, and a value default's absence from the reverse direction
(`parser-openapi` does read `schema.default`, see line 196) would make
round-tripping asymmetric only for `value` defaults — deferred rather than
half-implemented; tracked as an open question below.

## Nullability

- **3.1**: a nullable field's mapped schema gets its `type` widened to an
  array including `"null"` (`{ type: ['string', 'null'] }`), mirroring
  `typeMembers()`'s read side
  ([`packages/parser-openapi/src/parser.ts:67-80`](../../../packages/parser-openapi/src/parser.ts#L67-L80)).
  A `$ref` or `oneOf` can't carry `type` directly, so a nullable `ref` /
  `union` / `enum` field wraps in `{ oneOf: [<schema>, { type: 'null' }] }`
  instead.
- **3.0**: `nullable: true` is added as a sibling keyof the mapped schema
  (`{ type: 'string', nullable: true }`); a nullable `$ref` cannot carry
  `nullable` directly per the 3.0 spec (`$ref` siblings are ignored), so it
  is wrapped the same way as 3.1 forces via `allOf`: `{ allOf: [{ $ref }],
  nullable: true }` — the OpenAPI 3.0 idiom for "nullable + $ref".

## Required vs optional

`Field.optional` drives entity-level `required: string[]` (all non-optional
field names of that entity), exactly inverting
`required: !field.optional` from `parser-openapi`'s own `field()` builder.

## Relations

Decided: relations render nested, via `$ref` (the "deep" family in
`gen-zod`'s vocabulary — see
[`packages/gen-zod/src/render/relations.ts`](../../../packages/gen-zod/src/render/relations.ts)
for the family split this mirrors one side of). For each `Relation` on an
entity:

- `cardinality: 'one'` → property `{ $ref: '#/components/schemas/<target>' }`
  (or wrapped per the nullability rule above if `relation.optional`).
- `cardinality: 'many'` → property `{ type: 'array', items: { $ref:
  '#/components/schemas/<target>' } }`.
- Cross-source relations (`isCrossSource`, from `@kurotako/ir`) degrade to
  omitting the relation property entirely — same choice `gen-zod`'s deep
  family makes (logs at `debug`, see
  [`packages/gen-zod/src/render/relations.ts:36-41`](../../../packages/gen-zod/src/render/relations.ts#L36-L41)):
  v1 cannot reference a schema defined in another namespace's document.
- **Circular relations need no special handling**: unlike Zod/TypeScript,
  `$ref` in JSON Schema/OpenAPI is natively self- and mutually-recursive —
  there is no `z.lazy()`-equivalent problem to solve, and `ctx.cycles`
  (which `gen-zod` consumes for exactly this reason) is not needed by this
  generator.
- The relation property name is `relation.name`, added alongside the
  entity's own fields in the same schema object (no separate flat/deep
  schema pair per entity — decided: one schema per entity, not gen-zod's 5
  variants × 2 families).

## Artifact (`GeneratorArtifact`)

```ts
function buildArtifact(ir: IR): GeneratorArtifact {
  const entities: Record<string, EntitySymbols> = {};
  for (const [namespace, source] of Object.entries(ir.sources)) {
    for (const entity of Object.values(source.entities)) {
      entities[`${namespace}.${entity.name}`] = {
        module: `${namespace}/openapi/openapi.json`, // or .yaml per options.format
        symbols: { schema: `#/components/schemas/${entity.name}` },
      };
    }
  }
  return { entities };
}
```

No `dependsOn` — `gen-openapi` reads only the IR, like `gen-zod`. No
`peerDependencies` — the emitted document has no runtime import surface (no
generated TypeScript module to `import`). No `extra` — no other generator is
known to need OpenAPI-specific artifact data yet; add one only when a
concrete consumer needs it (nothing invented ahead of use).

## Serialization (`serialize.ts`)

- `format: 'json'` → `JSON.stringify(document, null, 2) + '\n'`.
- `format: 'yaml'` → the `yaml` package (already present transitively in the
  workspace lockfile through `@changesets/parse`, `@manypkg/tools`, etc. —
  becomes a direct `dependencies` entry for `@kurotako/gen-openapi`),
  `YAML.stringify(document)`.
- Deterministic key order for drift-guard purity: `document.ts` builds plain
  objects with a fixed key order (`openapi`, `info`, `paths`, `components`);
  `components.schemas` entries are inserted in a stable sort (entity/alias
  name, `localeCompare`) rather than `Object.entries` iteration order, same
  discipline `gen-zod`'s import-sorting already applies
  ([`packages/gen-zod/src/emit/entity.ts:444-447`](../../../packages/gen-zod/src/emit/entity.ts#L444-L447)).

## Errors (`errors.ts`)

One error class, `OpenApiGenError`, for the only failure mode intrinsic to
this generator: an entity or type-alias name that is not a valid OpenAPI
`components/schemas` key (the spec restricts it to `^[a-zA-Z0-9._-]+$`).
`parser-openapi` never produces such a name from a document it accepted, but
a name coming from `parser-prisma` (arbitrary model name) is unconstrained —
this generator is the first point where that constraint bites, so it is
enforced here, not upstream in the IR.

## Testing

`vitest`, unit tests per module (`render/schema.test.ts`,
`render/constraints.test.ts`, `document.test.ts`, `generator.test.ts`,
`serialize.test.ts`), plus one integration test asserting a full
`SourceIR` → parsed-back-as-valid-OpenAPI round trip (using the same
`@apidevtools/json-schema-ref-parser` dependency `parser-openapi` already
uses, to validate `$ref` resolvability of the emitted document — not to
re-run `parser-openapi` itself, which is a heavier, separate assertion this
feature does not need). Mirrors `packages/gen-zod/src/testing/ir.ts` for
`SourceIR`/`Entity` test builders rather than duplicating them.

## Open questions

- `Field.default` (`value` kind) emission as JSON Schema `default` — parked
  above, not blocking v1.
- Whether a future consumer generator needs `artifact.extra` (e.g. a
  client-codegen generator wanting the resolved document object directly
  rather than re-parsing the emitted file) — no such generator exists yet.
