# Output modes (directory / npm package)

**Status**: technical design — [technical.md](technical.md)

## Context

Each source produces its own submodule ([ADR-0004](../../../docs/adr/0004-ir-namespace-first.md)).
There are two ways to deliver it to the consumer: a directory inside the project (mode A)
or a real npm package per source (mode B). Both are retained
([ADR-0005](../../../docs/adr/0005-output-modes.md)); we need to specify their plumbing
and where it lives (in the core, in a dedicated module, in the CLI).

## Goal

The pipeline knows how to write the output in both modes, with the same module name
(`@kurotako/<ns>`) on the import side, and an A → B migration without changing the
application imports.

## Decisions made

### Module name and modes

- Mode A by default: `output.dir`, import by relative path or tsconfig alias.
- Mode B: `output.mode: package`, `packagesDir`, `scope`; `package.json` + `exports`
  generated by `tako`.
- Identical module name (`@kurotako/<ns>`) in both modes; A → B migration leaves
  application imports unchanged.

### Public API of a namespace

- **No aggregated barrel owned by the core.** Cross-generator imports already go through
  the typed manifest ([core-pipeline](../core-pipeline/overview.md)), not through an
  `index.ts`; an aggregated barrel would only add an eager-evaluation trap in
  non-bundled (Node / SSR) contexts and one more contact point to maintain.
- **Each generator emits the barrel of its own subtree** and decides what is public.
- The core additionally exposes **fine-grained `exports` subpaths** per entity
  (`@kurotako/pg/user`), so a consumer can import broadly or narrowly. Subpaths are
  deterministic.

### Mode B build and packaging

- Mode B runs a **build step per generated package** (`dist` + `.d.ts`) with **tsup**,
  so the package is publishable to a private registry, not only consumable as raw `.ts`.
- The generated `package.json` puts runtime libraries (`zod`, `@angular/forms`, …) in
  **`peerDependencies`** (provided by the consuming app), with a frozen `version`.
- The **list of peer dependencies comes from the generators**: each generator declares,
  in its contract/manifest, the runtime packages it requires (with a version range); the
  core aggregates them per namespace. Third-party generators work the same way.
- On the first `generate` in mode B, `tako` **runs the detected package manager's
  install** so the new `workspace:*` packages resolve. This install is a **CLI-level
  action, mode B only** — `@kurotako/core` still never installs anything.

### Mode A and version control

- **Mode A: `tako` only documents** the `@kurotako/*` → `output.dir` `paths` alias to add
  to the app's `tsconfig`. It never edits a file outside its own output directory.
- The output directory is **recommended to be `.gitignore`d** and regenerated in CI
  before build/test, consistent with core-pipeline's "`tako` is the exclusive owner, wiped
  every run".

### Generated-file marking

- Every emitted file starts with a `// Generated by tako. Do not edit.` banner.
- `tako` writes a `.gitattributes` in the output directory marking it
  `linguist-generated=true` (collapses diffs on GitHub for the rare committed case).

### Settled in technical.md

- Collision fix: each generator owns the `<ns>/<generatorName>/` prefix; the core
  synthesizes the namespace-root `<ns>/index.ts` (`export *` per generator).
- Plumbing lives **in `@kurotako/core`** (`packageWriter` beside `directoryWriter`, plus a
  barrel-synthesis step). `tsup` becomes a lazy mode-B dependency of core; no dedicated
  `@kurotako/output` package.
- Peer dependencies come from `GeneratorArtifact.peerDependencies`; the core aggregates
  per namespace and errors (`OutputPeerConflictError`) on conflicting ranges.
- Mode B `version` is a frozen `"0.0.0"`, never bumped.
- Package-manager for the mode-B auto-install: `output.packageManager` first, else
  lockfile detection, else the root `package.json` `packageManager` field, else print the
  command without spawning.
- Requires additive amendments to `core-pipeline`, `generator-zod`, `generator-angular`,
  `config-system`, `monorepo-bootstrap` — listed in `technical.md` "Consequences".

## Depends on

- [core-pipeline](../core-pipeline/overview.md), [config-system](../config-system/overview.md).
- Impacts every `gen-*` (path prefix `<ns>/<generatorName>/`, `artifact.peerDependencies`).
- **Ordering**: the barrel-synthesis + `<ns>/<generatorName>/` prefix half of this feature
  must land **before** `generator-zod` and `generator-angular` run together, otherwise they
  collide on `<ns>/index.ts`. Only the mode-B `packageWriter` can genuinely come last. The
  task cut should split the feature accordingly.
