# Drift Guard (`tako check`)

**Status**: technical design — [technical.md](technical.md)

## Context

Generated code is meant to be committed (mode A) or published (mode B). Without a
safeguard, it silently diverges from `schema.prisma` and the config: someone changes the
schema without re-running `tako`, or edits the generated code by hand. This is a classic
need, comparable to `prisma generate --check` or the generated-code checks of other
tools.

The vision explicitly places "CI / Drift Guard" out of the v1 scope
([docs/vision.md](../../../docs/vision.md#out-of-scope-for-v1)), which makes it a
legitimate backlog candidate for a later iteration.

## Goal

A `tako check` command that regenerates the output in memory, compares it to what is on
disk, and returns a non-zero exit code on any discrepancy, listing the files that drifted.
Its primary use is a **pre-commit hook**: before committing application code, confirm that
the generated code the app builds on is still in sync with the schema and the config.

## Decisions made

### Command

- **Dedicated `tako check` subcommand**, alongside `init` / `generate` / `validate`. Not a
  `--check` flag on `generate`: the intent is distinct and reads clearly in hook and CI
  logs. Owned by [cli](../cli/overview.md), which must add it to its command set.
- Runs the same pipeline as `generate` up to (not including) emission — so an invalid
  config or IR fails `check` the same way it fails `generate` (non-zero, error reported).
  Then it diffs the would-be output against the filesystem instead of writing.
- Global `--config <path>` applies. **No `--namespace` / `--generator` filter**: `check`
  verifies the whole output, consistent with core-pipeline's "full regeneration on every
  run" and the v1 "no incremental regeneration" rule.

### What counts as drift

- **Content difference** in a generated file.
- **Missing file** — the run would produce it, it is absent on disk.
- **Orphan file** — present in the output directory / package, the current run would not
  produce it (`tako` is the exclusive owner and wipes the tree on every `generate`).
- **Altered banner** — a generated file whose `// Generated by tako` banner was removed or
  changed. No special mechanism: the content diff catches it.

### Output

- **List of drifting files only**, one per line with a status marker
  (modified / missing / orphan). No unified diff, no per-file content — consistent with the
  CLI's "minimal by default, no `--verbose` / `--json` in v1" rule.
- Exit `0` when in sync, non-zero on any drift or any upstream error (invalid config, IR,
  driver failure).

### Scope by output mode

- **Mode A**: diff the whole `output.dir`.
- **Mode B**: diff `src/` + the generated `package.json` + `tsconfig.json` /
  `tsup.config.ts`; **ignore `dist/`** (a tsup build product, not deterministic generator
  output). `version: "0.0.0"` is frozen ([output-modes](../output-modes/overview.md)), so
  `package.json` diffs cleanly.

### Usage and CI

- **Pre-commit hook / local guard** is the target: catch a stale generated tree before it
  is committed with the app code that depends on it.
- **CI** is only meaningful when the generated code is versioned — mode A committed (the
  `linguist-generated` case) or mode B packages. In a CI that regenerates before
  build/test, `check` adds nothing and is not expected to run.

### Formatting hooks

- `tako check` does **not** run the `afterEmit` hook. A project that formats generated
  code through an `afterEmit` Biome/Prettier hook would see spurious drift. The contract:
  generators emit deterministic, already-formatted code; the `afterEmit` formatter is a
  `generate`-only convenience, documented as incompatible with `tako check`.

### Milestone

- **Post-v1 fast-follow**: kept out of v1 per [docs/vision.md](../../../docs/vision.md#out-of-scope-for-v1),
  but the first backlog item picked up after the MVP ships.

## Depends on

- [core-pipeline](../core-pipeline/overview.md), [cli](../cli/overview.md),
  [output-modes](../output-modes/overview.md).
- Reuses the in-memory regeneration path already introduced for `generate --dry-run`
  ([core-pipeline](../core-pipeline/overview.md)).
- Relies on the output directory ownership and the "generated" banner defined in
  [output-modes](../output-modes/overview.md).
- Assumes byte-deterministic generator output (same assumption the snapshot test strategy
  depends on).
