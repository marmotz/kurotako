# Documentation site — technical design

Design for the user-facing documentation site. Product decisions come from
[overview.md](overview.md); this document turns them into a concrete package, a site
generator configuration, a versioning workflow, an API-reference pipeline, and the list of
amendments the "new workspace + Pages deployment" decision forces on
[monorepo-bootstrap](../monorepo-bootstrap/technical.md).

## Starting point

- **No code exists.** The repo tree today is `docs/` (internal design docs), `backlog/`,
  editor/tool config. No `package.json`, no toolchain — see
  [monorepo-bootstrap/technical.md](../monorepo-bootstrap/technical.md).
- The GitHub repo `marmotz/kurotako` will be **public** (settled in
  [overview.md](overview.md)); GitHub Pages on a public repo needs no paid plan.
- This feature is downstream of a working toolchain and a stable public surface:
  [monorepo-bootstrap](../monorepo-bootstrap/overview.md),
  [cli/technical.md](../cli/technical.md) (the `tako` command surface it documents) and
  [config-system/technical.md](../config-system/technical.md) (the `tako.config.ts`
  reference it documents). It touches **no** package source; it only reads their public
  entry points for the API reference.
- Relevant design docs (external, absolute links):
  - [docs/vision.md](https://github.com/marmotz/kurotako/blob/main/docs/vision.md)
    — scope `@kurotako/*`, binary `tako`.
  - [docs/architecture.md](https://github.com/marmotz/kurotako/blob/main/docs/architecture.md)
    — the two output modes the site documents.
  - [docs/glossary.md](https://github.com/marmotz/kurotako/blob/main/docs/glossary.md)
    — `parser` / `generator` vocabulary the site must use.

## Package — `apps/docs`

New workspace at `apps/docs`, `package.json` `name` `@kurotako/docs`, `"private": true`.
The root `package.json` `workspaces` field gains `"apps/*"` alongside `"packages/*"`
(amendment to [monorepo-bootstrap #1](../../tasks/1-root-workspace-scaffold.md), see
[Amendments](#amendments-to-monorepo-bootstrap)).

```
apps/docs/
  package.json              # @kurotako/docs, private, Docusaurus deps + scripts
  docusaurus.config.ts      # site config (url/baseUrl, presets, plugins, navbar)
  sidebars.ts               # manual sidebar for the guide; API sidebar is generated
  tsconfig.json             # extends @docusaurus/tsconfig, NOT composite, NOT in tsc -b
  src/
    css/custom.css          # theme tokens
    components/              # only if a page needs a custom component
  docs/                     # the "current" (next) version content — tracked to main
    getting-started/
      quick-start.md
      installation.md
    concepts/
      parsers-and-generators.md
      intermediate-representation.md
      dependency-graph.md
      namespaces.md
    reference/
      tako-config.md
      cli.md
      catalog.md             # parser + generator catalog
      output-modes.md
    api/                     # GENERATED by TypeDoc, git-ignored in `docs/`, see below
  versioned_docs/            # frozen snapshots, created by `docusaurus docs:version`
  versioned_sidebars/
  versions.json
  static/
    CNAME                    # custom domain (value TBD, see Open points)
  build/                     # git-ignored
  .docusaurus/               # git-ignored
```

`apps/docs` is **not** a TypeScript project reference: Docusaurus ships its own
`tsconfig` and is built by its own CLI, not `tsc -b`. The root solution `tsconfig.json`
does not reference it; `bun run typecheck` at the root is unaffected. `apps/docs` has its
own `typecheck` script (`docusaurus typecheck` / `tsc --noEmit`) run only by the docs
workflow.

## Site generator — Docusaurus 3

TypeScript config (`docusaurus.config.ts`, `sidebars.ts`), `@docusaurus/preset-classic`,
`@docusaurus/tsconfig`. Installed and script-run with Bun like the rest of the monorepo
(Docusaurus documents Bun support; npm is the fallback if a Bun-specific bug appears —
this package is never published, so the "no `Bun.*`" rule does not apply here).

**Bun store + webpack (implemented workaround).** With Bun's store layout
(`node_modules/.bun/<pkg>@<ver>/node_modules/<pkg>` + symlinks), webpack's default
`resolve.symlinks: true` resolves every dependency under many real paths and the module
graph grows until the build runs out of memory. A tiny local plugin
(`apps/docs/plugins/webpack-symlinks/`) sets `resolve.symlinks: false` via
`configureWebpack`, which fixes it and keeps the Bun toolchain. The `typecheck` script is
`tsc --noEmit` (Docusaurus 3.10 dropped the `docusaurus typecheck` subcommand).

**`apps/docs/package.json` has no `"type": "module"`** (deviation from task #55). Docusaurus
emits its CommonJS runtime helpers (`.docusaurus/registry.js`, `routes.js`, …) with a
`.js` extension; under `"type": "module"` Node/webpack parse them as ESM and the server
bundle fails at runtime with `require.resolveWeak is not a function`. `create-docusaurus`
itself never sets the field. The rest of the monorepo stays `"type": "module"`.

### Why Docusaurus (alternatives considered)

The deciding constraint is **folder-per-version documentation with a version selector**,
no reliance on a content-archiving plugin, not necessarily React-tied.

- **Docusaurus** — retained. Folder-per-version is native and is exactly the chosen
  model: `docusaurus docs:version X` freezes the current `docs/` tree into
  `versioned_docs/version-X/` committed to git, and the navbar `docsVersionDropdown` is a
  built-in — zero custom plumbing. `docusaurus-plugin-typedoc` +
  `typedoc-plugin-markdown` are mature and integrate into the build. Cost: React/MDX
  runtime, the heaviest build of the candidates. Acceptable for a docs site built in CI.
- **VitePress** — rejected for this feature. Lighter and faster, but versioning is not
  first-class: it needs `@viteplus/versions` (smaller community, frozen `archive/<v>/`
  routes) or a DIY multi-tag build, and the version selector is then hand-wired. More
  moving parts for the one capability that drove the choice.
- **Starlight (Astro)** — rejected. Was the front-runner while a versioning *plugin*
  (`starlight-versions`) was on the table; with manual folders its natural answer is
  gone. Each version becomes a separate content-collection directory, the switcher a
  custom header override, and the per-version sidebar hand-maintained.
- **rspress** — rejected. Fast, MDX, but versioning is not first-class and the ecosystem
  (including `@rspress/plugin-typedoc`) is younger and smaller.
- **MkDocs Material + `mike`** — rejected. `mike` is the reference folder-per-version
  deployer, but the toolchain is Python, entirely off the project's Bun/TS stack, and it
  has no path to a TypeScript API reference.

## Content architecture

### First-publication scope (minimal, from overview)

`docs/` (the "next" version) ships:

- `getting-started/quick-start.md`, `getting-started/installation.md` — install `tako`,
  `tako init`, first `tako generate`. Sourced from
  [cli/technical.md](../cli/technical.md) command surface.
- `concepts/` — a **rewritten** user-facing pass over parser / generator / IR /
  dependency graph / namespaces. Written fresh for this audience; it does **not** import
  or transclude
  [docs/architecture.md](https://github.com/marmotz/kurotako/blob/main/docs/architecture.md)
  or
  [docs/glossary.md](https://github.com/marmotz/kurotako/blob/main/docs/glossary.md),
  which stay design documents. Where a design rationale matters, the page links to
  [docs/architecture.md](https://github.com/marmotz/kurotako/blob/main/docs/architecture.md)
  on GitHub.
- `reference/tako-config.md` — the `tako.config.ts` reference: `defineConfig`, the
  `parsers` map (config key = namespace), the `generators` array, `dependsOn`, `output`
  (`mode` / `dir` / `packagesDir` / `scope`), `hooks.afterEmit`. Mirrors
  `TakoConfigSchema` in [config-system/technical.md](../config-system/technical.md); the
  page is regenerated by hand when the schema changes (no automatic binding in v1).
- `reference/cli.md` — `tako init | generate | validate` (+ `--config`, `--watch`,
  `--dry-run`), from [cli/technical.md](../cli/technical.md).
- `reference/catalog.md` — the available parsers (`parser-prisma`) and generators
  (`gen-zod`, `gen-angular`), each linking to its own README / options.
- `reference/output-modes.md` — mode A (directory, default) vs mode B (npm package per
  source), from [output-modes/technical.md](../output-modes/technical.md) and
  [docs/architecture.md](https://github.com/marmotz/kurotako/blob/main/docs/architecture.md).
- `api/` — generated (next section).

Deferred to a fast-follow (overview): the "writing a parser" and "writing a generator"
guides, which belong with the future `plugin-kit` / `parser-kit` feature.

## API reference — TypeDoc

`docusaurus-plugin-typedoc` (wrapping `typedoc` + `typedoc-plugin-markdown`) runs as part
of `docusaurus build`.

- **Entry points**: the four public packages, via
  `entryPointStrategy: "packages"` — `packages/ir`, `packages/core`, `packages/config`,
  `packages/cli` (each package's `src/index.ts`; `cli` additionally documents its
  programmatic `runCli`). Parser/generator packages are covered by `reference/catalog.md`
  prose in v1, not TypeDoc.
- **Output**: Markdown written into `apps/docs/docs/api/` with a generated sidebar slice
  merged into `sidebars.ts`. `apps/docs/docs/api/` is git-ignored on the `next` version
  (regenerated every build).
- **Versioned with the docs**: because `docs:version X` snapshots the whole `docs/` tree,
  the generated `api/` is produced **before** the snapshot and frozen into
  `versioned_docs/version-X/api/`. Consequence: cutting a version commits a body of
  generated Markdown to git (bounded — four packages, and only on release). This was
  chosen over an always-latest single API section, which would misdescribe older
  releases.
- **Project constraint**: public exported symbols of the four packages carry TSDoc.
  Enforced softly at first (TypeDoc `--validation.notDocumented` as a warning in the docs
  workflow); a hard gate can come later. This constraint is recorded here and belongs in
  each package's technical design as it is written.

## Versioning workflow

- **Selector key**: the version dropdown tracks `@kurotako/cli` (`tako`) releases. The
  independently-versioned packages (changesets, see
  [monorepo-bootstrap/technical.md](../monorepo-bootstrap/technical.md)) are **not**
  surfaced individually; the docs version is "the docs as they stood for `tako` vX".
- **`next`**: `docs/` tracks `main`, published at `/next/`. It is the only content until
  the first `tako` release — no frozen version, the dropdown stays hidden
  (Docusaurus shows it once `versions.json` is non-empty).
- **Cutting a version**: on a `@kurotako/cli` release, a maintainer runs
  `bun run docusaurus docs:version <major.minor>` in `apps/docs`, commits
  `versioned_docs/` + `versioned_sidebars/` + `versions.json`. The workflow is manual and
  documented in `CONTRIBUTING.md` (amendment to
  [monorepo-bootstrap #10](../../tasks/10-repo-meta-files.md)).
- **Latest served at `/`**: `docusaurus.config.ts` sets the most recent frozen version as
  `lastVersion` once one exists; until then `next` is served at `/`.
- Only `major.minor` granularity — patch releases do not cut a docs version.

## Deployment — GitHub Pages

Dedicated workflow `.github/workflows/docs.yml` (separate from `ci.yml`):

```yaml
name: docs
on:
  push:
    branches: [main]
    paths:
      - 'apps/docs/**'
      - 'packages/*/src/**'          # API reference inputs
      - '.github/workflows/docs.yml'
  workflow_dispatch:
permissions:
  contents: read
  pages: write
  id-token: write
concurrency:
  group: pages
  cancel-in-progress: false
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
        with: { bun-version-file: package.json }
      - run: bun install --frozen-lockfile
      - run: bun run --filter '@kurotako/docs' build
      - uses: actions/upload-pages-artifact@v3
        with: { path: apps/docs/build }
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: { name: github-pages, url: '${{ steps.deployment.outputs.page_url }}' }
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

- `bun run --filter '@kurotako/docs' build` also runs TypeDoc against the four public
  packages. TypeDoc resolves their public types from the built `dist/*.d.ts` (the repo
  has no `@kurotako/* -> src` path mapping), so the workflow runs
  `bun run --filter './packages/*' build` **before** the site build. The root
  `bun run build` is scoped to `./packages/*` — the docs site is built by this workflow
  only and never gates package CI (`ci.yml` unchanged).
- **Custom domain**: `baseUrl: '/'`, `static/CNAME` holding the domain, GitHub Pages
  "Custom domain" set once in repo settings, "Enforce HTTPS" on. The exact domain is an
  open point (see below); until it is chosen the site can ship at
  `https://marmotz.github.io/kurotako/` with `baseUrl: '/kurotako/'` as a one-line flip.
- `ci.yml` (the toolchain workflow) is **not** modified; docs never gate package CI and
  vice versa.

## Consequences verified against the current repo

- Nothing to migrate: no code exists. `docs/` at the repo root is untouched and stays the
  internal design space; the site lives entirely under `apps/docs/`.
- The `vitest.workspace.ts` glob (`packages/*/vitest.config.ts` per
  [monorepo-bootstrap/technical.md](../monorepo-bootstrap/technical.md)) does not pick up
  `apps/docs` — the site has no unit tests. A link-check / build-smoke in `docs.yml` is
  the only automated check.
- `bun install` at the root will now also resolve `apps/docs` Docusaurus deps (a large
  tree). Acceptable; contributors touching only packages still pay it. A `--filter`
  install is possible later if it hurts.
- The first frozen version cannot be cut until `@kurotako/cli` has a release, which is
  after the MVP (`parser-prisma` + `gen-zod` + `gen-angular` + `cli`) works end to end
  ([docs/vision.md](https://github.com/marmotz/kurotako/blob/main/docs/vision.md)). Until
  then the site is `next`-only and the "version selector from v1" decision is satisfied by
  the mechanism being in place, not by a second version existing.

- `preset-classic` blog: off for v1 (no blog decided). Revisit if release notes want a
  home other than the changelog.
- i18n: English only ([AGENTS.md](https://github.com/marmotz/kurotako/blob/main/AGENTS.md));
