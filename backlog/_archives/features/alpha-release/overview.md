# First public release (0.1.0)

**Statut** : conception technique — voir [`technical.md`](technical.md)

## Contexte

The MVP feature set is implemented and archived (`monorepo-bootstrap` → `output-modes`,
plus `docs-site`, `meta-package`, `drift-guard`, `e2e-examples`, `monorepo-projects`,
`driver-options-ergonomics`). See [`_archives/done.md`](../../_archives/done.md).

Infrastructure already in place:

- The GitHub repo `marmotz/kurotako` is **public**, MIT licensed.
- The documentation site is **live** at <https://kurotako.marmotz.dev/>, deployed
  automatically by [`docs.yml`](../../../../.github/workflows/docs.yml) on push to `develop`
  (GitHub Pages, custom domain, HTTPS active).
- [`ci.yml`](../../../../.github/workflows/ci.yml) runs on the default branch.

What still blocks a public release:

- All eight publishable packages sit at `version` `0.0.0`.
- [`release.yml`](../../../../.github/workflows/release.yml) is disabled and no `NPM_TOKEN`
  secret is wired; the npm org `kurotako` does not exist yet.
- Six unconsumed changesets (real, merged features) are queued under
  [`.changeset/`](../../../../.changeset/) and have never been versioned.
- `.changeset/config.json` has `baseBranch: main`, but the default branch is `develop`.
- `README.md` still says "Status: design phase" / "packages are scaffolded empty";
  root [`AGENTS.md`](../../../../AGENTS.md) still says "No implementation code exists yet"
  and "private".
- Per-package `package.json` metadata (`description`, `keywords`, `repository.directory`,
  `homepage`, `bugs`, per-package `README.md`) is not release-ready.

## Objectif

Publish `kurotako` and `@kurotako/*` to npm as `0.1.0` — the first version an external
user can `npm install` and run — with the repo docs and contributor files accurate for
a published project. `0.x` itself signals that the API is not yet stable; there are no
semver guarantees during the `0.x` line.

Non-goals: a `1.0.0`, API-stability commitments, marketing, new product capabilities,
documentation versioning.

## Décisions actées

### Versioning

- First release is a plain **`0.1.0`**, no pre-release suffix, published under the
  **`latest`** dist-tag (`npm install kurotako` just works). "alpha" is not part of any
  version string; instability is communicated by `0.x` + a note in README/docs.
- For this first cut, **all eight packages go to `0.1.0` together**, via a single
  changeset run through `changeset version` (which also writes each `CHANGELOG.md`).
- **After** `0.1.0`, versioning stays **independent** per package (current changesets
  config unchanged — no `fixed`/`linked`); numbers may diverge from then on.
- Internal deps move from `workspace:*` to **`workspace:^`** so a patch of one internal
  package does not force re-releasing every dependent.
- The six pending changesets are **deleted and replaced by a single** "initial
  `0.1.0` release" changeset (minor, all packages), for a clean first CHANGELOG.
- `.changeset/config.json` `baseBranch` is corrected to `develop`.

### npm publishing

- The npm org **`kurotako` must be created** and an `NPM_TOKEN` automation token wired
  as a repo secret (manual, user-side prerequisites). `access: public` is already set.
- [`release.yml`](../../../../.github/workflows/release.yml) stays **manual
  (`workflow_dispatch`)** for now — every npm publish is a deliberate action. Enabling
  push-triggered publishing is deferred.
- Before the real run: `changeset publish --dry-run` / `npm pack` inspection of every
  package (files, `exports`, `bin`, and that the `workspace:` ranges are rewritten to
  real versions in the tarballs).
- npm **provenance** is enabled on `release.yml` (signed build attestation, low cost
  since publish already runs in CI).
- Each published package gets a `README.md`; `CHANGELOG.md` files are generated by
  changesets; a light root `CHANGELOG.md` points to them and to GitHub Releases.

### Documentation site

- Hosting is **done** — no work beyond making sure the site content and `README.md`
  reflect `0.1.0` (drop "design phase", add an install + quickstart section against the
  published package) and carry a short "0.x, API may change" note.
- Docs stay **single-version ("current")**; Docusaurus versioning is introduced later,
  around `1.0`.

### Repository hygiene

- Refresh `README.md`, root `AGENTS.md`, `CONTRIBUTING.md` (stale toolchain rows) and
  the `docs/vision.md` status wording (remove "design phase" / "no code" / "private").
- Add `SECURITY.md` and GitHub issue / PR templates.
- Consider branch protection requiring `ci.yml` on `develop` (to confirm).
- `scripts/release-publish.sh` creates the per-package `pkg@0.1.0` tags and one GitHub
  Release per package. No umbrella `v0.1.0` tag (versions are independent).

### Proposed rollout order

1. Fix `baseBranch`, replace the six changesets with the single `0.1.0` one; migrate
   internal deps to `workspace:^`.
2. Per-package `package.json` metadata + per-package `README.md`.
3. Refresh root `README.md` / `AGENTS.md`; add `SECURITY.md` + templates.
4. User creates the npm org.
5. Set all packages to `0.1.0`, dry-run publish, inspect tarballs.
6. First `0.1.0` publish: manual + local (`npm login`, `bun run release`) — no trusted
   publisher can exist yet. Then configure a trusted publisher per package on npmjs.org;
   every release after runs `release.yml` with no secret. Per-package tags + Releases are
   created by `scripts/release-publish.sh`.
7. Smoke test: `npm create` / `bunx tako init` in a clean project against the published
   `0.1.0`.

## Depends on

Nothing new — downstream of the entire archived MVP backlog.
